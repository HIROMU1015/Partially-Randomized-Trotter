## 2. 実装全体の原則

### 2.1 固定DFモデルだけを扱う

初期の数学的対象は、

\[
H_{\mathrm{DF}}
=cI+Q+\sum_{\ell=1}^{r}\lambda_\ell A_\ell^2
\]

とします。

\[
Q=\sum_{pq}q_{pq}a_p^\dagger a_q,
\qquad
A_\ell=\sum_{pq}(g_\ell)_{pq}a_p^\dagger a_q.
\]

条件：

- 固定N sector
- Hermitianなq、g_l
- 実数c、λ_l
- 符号付きDF平方
- 全fragmentがparticle numberを保存
- 固定順序の正stage対称二次PF
- binary64係数を正確な有理数として解釈する固定DF target

元の分子Hamiltonianへの厳密な対応は、今回の認証対象ではありません。

DF分解、SCF、FCI、積分生成、DF rank選択、ground solveは実行しないでください。

### 2.2 正確な演算と検証

認証用の数値は原則としてexact integer / rational arithmeticを使用してください。

科学的な数値をJSON floatとして保存しないでください。

浮動小数点の表示値や数値eigensolverの出力を、数学的certificateへ格上げしてはいけません。

### 2.3 Generatorとcheckerを分離する

認証値を作るgeneratorと、それを検査するcheckerを明確に分けてください。

checkerはgeneratorのsuccess flagを信頼せず、元のraw bits・宣言された条件・証拠から必要な等式・不等式を再検証します。

同じ計算関数を二度実行しただけで「独立検証」と呼ばないでください。

schemaやcanonical serializationなど、安全に共有できる基盤は共有して構いません。ただし、科学的に重要な係数復元・scalar再構成・cap検算については、独立性の範囲と共通依存部分を明記してください。

## 3. SPEC-01：Exact Model Intakeとidentity

### 3.1 Binary64 exact decode

固定DFモデルの係数を、IEEE 754 binary64のbit patternから正確な有理数へ変換するSOURCEを実装してください。

対応事項：

- sign / exponent / fraction
- normal / subnormal
- +0 / −0
- complex128の実部・虚部
- 正確な分数への変換
- 正規化されたRat形式
- NaN / Infの拒否
- dtype・shape・endianの検査

decode時に、binary64の算術誤差を新たに混入させないでください。

`float`で計算してから分数に近似する実装ではなく、保存bit patternの正確な解釈を基準としてください。

### 3.2 ModelIntake

設計資料の`ModelIntake`仕様に従い、次を扱ってください。

- raw inputのidentity
- exact coefficient table
- constant
- one-body matrix
- 全λとg matrices
- mode数・mode順序
- 単位
- 対象モデルの意味論version
- provenance
- 変換履歴
- 元分子との対応が未認証であることの明示

初期入力は`DFHamiltonian`のfull constant / full one-body / signed squaresです。

`DFModel`のcorrection-only表現と、field名だけで混用してはいけません。

`df_truncation_value`をconstantへ足さないでください。

部分blockだけの入力を、全Hamiltonianの認証へ流用してはいけません。

### 3.3 Hermiticityと入力拒否

exact係数について、

\[
q=q^\dagger,\qquad g_\ell=g_\ell^\dagger
\]

を検査してください。

また、cとλの実数性、mode数、配列shape、block inventoryを確認してください。

不成立の場合はfail-closedとします。

`hermitized()`、`real_if_close()`、暗黙cast、対称化によって入力を勝手に修復してはいけません。

モデルが不正なら、設計で定義された理由付きverdictを返してください。

### 3.4 Canonical identity

設計資料の型とhash規約を実装してください。

- `Int / Nat / Rat / ComplexRat`
- `MatrixRef`
- `Digest / ObjectRef`
- canonical serialization
- 内容に基づくSHA256
- raw identityとexact model identityの分離
- version付きの意味論
- 重複key拒否
- 整数・有理数の正規化
- key順序と配列順序の固定

少なくともSPEC-01〜03で必要な、

`model_id → sector_id → partition_id → pf_id`

の依存関係を扱えるようにしてください。

将来のbundle/comparison identityについては、共通型を用意してもよいですが、**SPEC-04〜07を完成したかのように実装・出力しないでください。**

未生成の科学certificateを、placeholder値でPASSにしないこと。

## 4. SPEC-02：Sector・PF・scalar台帳

### 4.1 固定N sector

対象は固定粒子数Nです。

少なくとも次を検証してください。

\[
0\le N\le n_{\mathrm{modes}}
\]

- mode順序
- occupation-bit規約
- JW/fermionic ordering
- CAR convention
- 全基本項のnumber conservation
- identity・一体項・平方項のsector保存

単に古典的なsector indicesを抽出しただけで保存則の証明としないでください。

基底外遷移をskipしただけの計算結果も証拠にしないでください。

固定Nα/Nβ、S² sector等への拡張は今回不要です。

### 4.2 PF順序

固定した正stage対称S2について、

\[
S_2(h)
=
e^{-ihF_1/2}\cdots
e^{-ihF_M}\cdots
e^{-ihF_1/2}
\]

の表示順、回路時系列、fragment identityを明示してください。

検査事項：

- palindrome
- half-stageと中央stage
- 各fragmentの総時間係数が1
- 全block inventoryとの一致
- 零fragmentの扱い
- 表示順と実装時系列の対応
- fragment順序が変わる場合の別identity

SPEC-02では、実際の量子回路の生成やcompileは行いません。

### 4.3 Scalar ledger

各fragmentを、

\[
F_j=B_j+s_jI
\]

と表現し、元のDF Hamiltonianとの恒等式を保つscalar台帳を実装してください。

特に、

\[
L+\sum_j s_j=c
\]

を正確に検査してください。

核反発、constant correction、negative-square shift、PF controlled phaseを二重加算しない設計を維持してください。

SPEC-03で生成するL・shift・fragment capsと接続できる構造にしてください。

単にscalar値の数値的一致だけでなく、全寄与の由来とcontext identityを保存してください。

## 5. SPEC-03：PSD・L・f_j・Λ

今回の主要な数理認証実装です。

既存K0のPSD化を正確な係数演算と独立checkerへ接続してください。

### 5.1 正確な一体operator cap

Hermitian一体係数行列xについて、

\[
s_x=
\sum_{pq}
\left(
|\operatorname{Re}x_{pq}|
+
|\operatorname{Im}x_{pq}|
\right)
\]

を正確な有理数として求めます。

初期の安全なcapは、

\[
q_-=-s_q,\qquad q_+=s_q,
\]

\[
u_\ell=s_{g_\ell}
\]

です。

これらは既知のoperator norm三角上界による保守的な認証値です。

**より鋭いcapの新規探索・数値eigensolverへの置換は今回行わないでください。**

generatorはcapとその導出情報を出力し、checkerは正確な係数から独立に再検算してください。

### 5.2 Signed PSD化

各fragmentを次の既知式で構成します。

**一体項**

\[
F_0=Q-q_-I
\]

\[
f_0=q_+-q_-.
\]

**正符号平方**

\[
\lambda_\ell\ge0:
\quad
F_\ell=\lambda_\ell A_\ell^2,
\qquad
f_\ell=\lambda_\ell u_\ell^2.
\]

**負符号平方**

\[
\lambda_\ell<0,\quad\mu_\ell=-\lambda_\ell:
\]

\[
F_\ell=\mu_\ell(u_\ell^2I-A_\ell^2),
\]

\[
f_\ell=\mu_\ell u_\ell^2.
\]

これらが同じsectorで、

\[
0\preceq F_j\preceq f_jI
\]

を満たす根拠を検証してください。

### 5.3 LとΛ

下界は、

\[
L=c+q_-
-\sum_{\lambda_\ell<0}\mu_\ell u_\ell^2.
\]

また、

\[
\Lambda=\sum_j f_j.
\]

検査事項：

- 全符号の場合のfragment式
- 各PSD性
- 各capの正当性
- scalar寄与
- 元DF Hamiltonianとの正確な演算子恒等式
- 全blockの対応
- fragment順序
- LとΛの単位
- 零λと零cap
- context IDの一致

LやΛを表示用に丸めた値から再構成しないでください。

上向きcapを採用した場合、そのcapを対応するnegative-square fragmentの定義にも使用してください。

shift後fragmentとshift前capを混同してはいけません。

### 5.4 証拠形式

少なくとも次を扱ってください。

- `LowerCertificate`
- `FragmentCapCertificate`
- 対応するgenerator
- 対応する独立checker
- 理由付きverdict
- parent IDs
- SOURCE/version
- witness references
- exact values
- scalar ledger
- partial failure record

これらの証拠を使ってL・全f_j・Λを再検証できるようにしてください。

実装に必要な具体的class名・module構造は、既存namespaceとの衝突を避けながらCodexが決めて構いません。

ただし、文書仕様との対応を明確に残してください。

## 6. 許可する人工テスト

実際の分子データ、保存済みHamiltonian、既存のheld-out入力をfixtureとして使用してはいけません。

### 6.1 Positive tests

少なくとも次を含めてください。

- binary64 normal / subnormal
- 正負の値
- +0 / −0
- 実・複素Hermitian行列
- 対角・非対角の一体項
- 正符号・負符号・零λ
- signed PSD shift
- 固定Nの端点
- 一体項だけのM=1
- λ=0やcap=0を含むfragment inventory
- exact scalar恒等式
- exact L / f / Λ
- 同じmodel内容からのidentity再現性
- 合法なPF順序とhalf-stage

人工入力は、手計算で期待値を求められる例を優先してください。

必要に応じて人工的な小行列のexact algebraを使った照合は可能ですが、**その結果を科学的benchmarkや実分子certificateへ流用しないこと**。

### 6.2 Negative tests

少なくとも次を拒否できるようにしてください。

- NaN / Inf
- 不正なdtype・shape・endian
- 非Hermitian入力
- 複素対角成分の不正な虚部
- 不正なλやconstantの型
- full/correction-onlyの規約混用
- scalarの二重加算
- 不正なN
- 不整合なmode ordering
- 欠けたblock / 不正なinventory
- PFの非対称なstage構成
- fragment順序の不一致
- capの過小申告
- Lの過大申告
- Λの過小申告
- 異なるmodel/sector/partitionの証拠流用
- hash・witnessの改変
- partial certificateを完全認証として扱う誤り

### 6.3 独立checkerの検証

generatorが作成した正常な人工証拠がcheckerで受理されることに加え、証拠を意図的に改変して拒否されることを確認してください。

特に、

- capだけを小さくする
- scalarだけを変更する
- fragment符号を変更する
- λ・gの一部を変更する
- mode順を変更する
- PF順序だけを変更する
- parent IDを差し替える
- raw bitsとexact係数を不一致にする

といったmutation testsを実施してください。

checker自身がgeneratorと同じ誤りを共有する可能性についても、独立した人工oracleや手計算で重要部分を検証してください。

### 6.4 テストの実行境界

許可するのは、今回作成したSOURCEと、既存の関連する技術的テストです。

既存のテスト名だけから安全と推定せず、実際の科学データ取得、SCF/FCI、DF生成、native compile、科学的再解析を起動しないことを確認してから実行してください。

テスト失敗時は、今回許可したSOURCE内で原因調査・修正・再テストを行って構いません。
