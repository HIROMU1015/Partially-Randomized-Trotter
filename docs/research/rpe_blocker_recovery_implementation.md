# RomuTail中央制御　探索の詰まりを自動解消する実装指示

**実装担当は中央制御のCodex。** 通常のStartで受け付けた探索について、信号・価格・監査・Q3・結果回収のいずれかが詰まったとき、RomuTailが原因を特定し、元証拠の取得、必要な検証の配送、採否決定、同じ候補の探索再開までを進める。利用者が候補ごとに別チャットへ検証を依頼する作業をなくす。適用先は新規runと、通常手順で互換性を確認して引き継ぐrun。

本書は実装・検収の仕様。下記の履歴は再現材料であり、着手時の本番状態は中央で確認する。新規の科学計算や科学的再解析には、そのrunに対して利用者が許可した範囲と既存契約を適用する。

## 2. 各理由に対して中央が行う操作

判断単位は、固定契約で独立に扱える最小単位とする。信号は物理候補とラウンド、価格は回路・経路と測定軸、Q3は回路・入力・評価契約と整数配分。出所・精度・予算を含む既存の同一性判定を使う。同じ入力を要求する複数候補は一つの仕事を共有する。

| 確認したこと | 自動で行うこと | 決着または再開の条件 |
|---|---|---|
| 保存索引には値があり、元receiptが手元にない | 現run・継承run・登録済みの固定Git参照・元workerまでたどる。大きな原本は保存元で照合し、必要な証拠のみ転送する。 | 固定入力・結果・終了証跡・当該工程の受入規則が一致すれば元成果を採用。「存在しない」「照会不能」「内容不一致」を個別に記録する。 |
| compileが終了し、価格の監査が未完 | 元compileの出力と軸を固定して監査を配送する。親工程が失敗していても、子の正常終了と出力を独立に受理できるか調べる。 | 監査済み軸だけを価格に登録する。部分ファイルだけでは成功扱いにしない。 |
| 適用可能に見える価格モデルが複数、または対象が較正範囲外 | 同条件の直接価格、較正と独立検証の元データ、適用範囲を順に照合する。既定規則で一意なら採用。残りは既存契約が認める該当点の直接取得または独立検証を計画する。 | 先に「どの結果ならどの軸が確定するか」を固定する。一点の実測は当該点で使用し、モデル全域への適用や再fitには別の科学条件が要る。複数の有効な直接証跡が食い違う場合は出所まで戻る。 |
| 信号、descriptor、価格の一部が足りない | 同じ物理条件の保存分を採用し、必要なラウンド・軸だけを要求する。信号と価格が独立なら並行して進める。 | X/Yに同じ経路が必要ならseed・event digestを共有し、軸別receiptを確認する。X/Yや実行hostの違いを独立標本に数えない。 |
| 評価器または数値条件が合わない | 固定route・Python・provider・descriptor・λ・整数配分・精度を元要求と比較し、最初の差を特定する。通常Q3／大ショットQ3は要求との互換性で選ぶ。 | 既知の互換環境で一致したら配送を再開。大きな $M$ では評価器、候補の終端信号、総費用用の終端価格を個別判定する。閾値、幅、整数グリッドを変える必要がある場合は現条件で未評価とする。 |
| 同一評価に実行所有がある、または送信・終了応答がない | 元job・attempt・hostをたどり、プロセス、PBS状態、終了receipt、spoolを照合する。完了済み未転送なら同じattemptから回収する。 | 所有中・終了未確定の同一計算は追加起動0件。終了済みで成果がなく、契約で再試行できる場合だけ不足分を一度予約する。 |
| 実行できるhostがない | 固定コード・依存・bundle・runtime・軸入力を割当前に確認する。専用環境へ不足分だけを配布して再照合し、先に適格になったhostへ配送する。 | host復帰、容量回復、十分なCPU・RAM・残りwalltimeが得られたときに対象要求を再照会する。手動Pauseと科学STOPは保持する。 |
| 照会先を尽くした、同じ失敗が続く、または規則にない問題が出た | 対象、最初に失敗した工程、調べた証拠、元のログ、再現手順、適用できる既知の修正を一組にまとめてStatusから辿れるようにする。 | 実装不具合はCodexが回帰例を作り、修正版の通常リリース手順へ進める。新しい科学判断・未承認の計算・契約変更だけを利用者にまとめて返す。独立候補は継続する。 |

新規計算の結論は「不足分を計算する」か「現条件で新規起動しない」の二択。後者では**再利用済み、元attemptを追跡中、未評価で終了**の内訳を残す。予算終了・STOP・再試行禁止・旧所有を解消できない場合は理由を明示する。未評価はMSE不適合・最安確定・範囲全体の完了に数えない。

## 3. 実装順

1. **通常入口から現在の行き止まりを棚卸しする。** 既存の `price_actions`、`DF_PRICE_DECISIONS.json`、候補状態、台帳を使い、理由ごとに「既に動く」「判定はあるが次操作につながらない」「現契約では実行不能」を整理する。各判断に対象単位・根拠の参照・次の担当と操作・再判定条件を持たせる。旧runで追加項目が欠ける場合も従来の記録を読めるようにする。
2. **最初にPR-DFで一往復させる。** 下記の26軸を再現例に、保存証拠の発見、既存規則による採否、残る最小検証の生成、workerでの実行、RomuTailでの採用、同じ候補のREADY通知まで接続する。検証REQUESTには解く問い、固定入力と参照元、判定規則、戻し先を持たせる。証拠で判定できないときは次に必要なものを特定する。候補ID、モデルID、軸数を実装の分岐条件にしない。
3. **全方式と工程に広げる。** Full PF・B0Iの片軸と監査回復、PR-Pauliの入力receipt、共通信号、追加ラウンド、大小ショットのrouteを同じ処理へ接続する。各方式の科学判定は元の実装へ渡す。ある候補の競合中にも、準備済み配分のQ3や独立の準備を実行する。
4. **各hostへの配送を通常の予約に載せる。** RomuTailが候補選択・予算・採否を所有する。重い検証、compile、監査、数値評価は要求を満たす空きworkerへ配る。RomuTailの32 CPUは中央処理を優先し、余力でworkerを動かす。server1・2は各30 CPU、PBSは取得済み96 CPUノードと現行の予約上限、WSLは稼働時の受付・現行profileに従う。上限はCPUの合計で管理し、準備とQ3でCPU・RAMを二重予約しない。既存の50 GiB上限・40 GiBからの整理と受付復帰を使い、中央自身のworker容量が不足しても中央の配送・採用は続ける。
5. **再起動と通知競合を扱う。** 保存価格到着、receipt到着、host復帰、入力更新、予算変更で、影響を受ける単位だけを起こす。イベント欠落は通常Resumeと定期照合で回復する。複数候補が同じ証拠を待っても予算予約・起動・採用は各一回。中央が採用直後に停止しても、再開時に候補への反映を完了できるようにする。重い報告・マップ生成は、必須の台帳保存後に進める。
6. **供給が途切れた理由を見えるようにする。** 次の探索判断に必要なQ3と、多くの候補を進める共通準備を優先する。任意の追加モデル検証は低優先。実行中に次の適格候補を先に照合し、先行結果に依存する候補はその結果を待つ。Statusでは「独立した仕事が尽きた」「共有入力待ち」「適格host不足」「配送・回収・採用待ち」を区別する。同じ証拠の走査を繰り返す場合は、元情報・固定版が変わった単位だけ再照合する。

## 5. 実装完了の報告

- 主要な詰まりごとに、**自動で解決した数、元attemptで追跡中の数、現契約では未評価の数と理由**を示す。未評価に必要な判断があれば対象と選択肢をまとめる。予約・受領・実行開始・正常終了・科学結果採用を別々に数える。
- 改善前後で、詰まり検出から次操作、READYから割当、結果受領から採用までの時間を既存計時で比較する。host別の適格な待機仕事、実際に開始した工程、子を含む科学CPU時間、測定区間と利用可能CPUを併記する。独立仕事がなかった区間を分け、人工検収だけで実探索の高速化を結論しない。
- 変更点、既存のまま再利用した経路、人工／保存／許可済み実runの検収範囲、残る科学判断を引き渡す。本番適用の対象が指定された際は、固定SOURCE・入力・予算・STOP・未確定attemptを通常のrelease／継続手順で照合する。共通の運用ルールには、検収を通った動作を追記する。

## 6. 実装と検収の記録

- **PR-DF**。元compileが別の価格グループにあっても、既存要求と同じ物理軸を照合する。現runの台帳で受領済みなら、元jobから回収して監査へ渡す。先行runの固定された終了結果も既存のpath検査へ渡す。元attempt・登録済みGit参照・価格台帳が変化した際に再判定する。価格判断には軸、出所、必要な根拠、既知の元job・attempt・状態を記録する。
- **PR-Pauli**。価格競合で信号を延期した旧記録から、通常の分散準備で信号を取得して保持する。価格が確定したら同じ候補を戻す。Full PF・B0Iは軸別の保存照合とC監査を再利用する。準備キューでは、予算や停止で未割当だった固定要求を既存の予約に戻せる条件を追加した。
- **保存PR-DF例**。上記の候補について、固定設定・基礎quote・中央の保存価格台帳を読み取りで照合した。基礎quote単体では26軸とも物理分割に合う価格がなく、保存価格台帳を適用すると26軸すべて `REUSE_PRICE` になった。新規較正計画は0件。過去の競合14軸と範囲外12軸は履歴として保持し、当時の未解決分岐は人工入力で検査した。
- **人工検収**。価格照合、候補準備、途中の結果回収、工程予算、分散キュー、PBSの所有管理の118テストと8サブテストが通過した。固定した人工checkoutで、通常入口・同期の33テストと2サブテストが通過した。実CLIでPreview、Start、Stop、Resumeを実行し、Windowsと同じ要求形式でStatusを取得した。初回評価1件、同じrunのResumeで追加評価0件。Windowsの実機実行、PBS実機、実探索での速度測定は未検収。
- **既存の試験失敗**。WSL転送のテスト1件は `scp` を期待し、実装は `ssh` を呼ぶ。実装前のコードでも同じ差を再現し、今回の結果とは区別した。
- **適用範囲**。作業worktreeの実装と人工検収まで。本番releaseの切替と新規科学計算は0件。契約上の価格採否が決まらない軸と、終了確認が取れない元attemptは個別に残る。対象runの固定版を切り替える際は、通常のrelease／継続手順で所有とSTOPを照合する。
